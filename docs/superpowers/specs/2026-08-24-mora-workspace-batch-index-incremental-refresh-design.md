# Mora 工作区批量索引与增量刷新设计

> 日期：2026-08-24
>
> 状态：已确认，进入实施计划

## 1. 背景

Mora 已有两条相互独立的能力：

- `workspace.rs` 递归扫描用户打开的文件夹，生成 `.md`、`.mdx` 目录树，最多返回 10,000 个目录和文件条目。
- `note_index.rs` 把用户已经打开或保存过的笔记写入应用数据目录中的 `notes-index.json`，供“工作区查找”按标题、标签和正文搜索。

当前打开文件夹只建立路径树，不读取全部正文。因此，一个从未在 Mora 中打开过的工作区文件不会出现在搜索结果中；目录刷新也不会增量更新搜索索引。用户已经确认本次增加工作区批量索引，并在既有刷新时机中只处理新增、变化和删除的文件。

## 2. 已确认需求

- 打开或恢复工作区文件夹时，递归索引扫描结果内的全部 `.md`、`.mdx` 文件。
- 后续刷新通过磁盘修改时间和文件大小识别未变化文件，不重复解析其正文。
- 新增和变化的文件重新读取并写入索引；已删除文件从对应工作区范围的索引中移除。
- 窗口重新获得焦点、左侧文件夹刷新按钮和“工作区查找 → 刷新列表”都触发增量刷新。
- `.mdx` 必须继续执行 MDXNote ZIP 和 manifest 校验；普通 `.md` 复用现有 Front Matter 解析。
- 单个文件损坏、读取失败或格式无效时，整批刷新继续执行，并返回失败统计。
- 失败文件保留上一次有效索引，等待下次刷新重试，避免一次临时读写冲突清空可用搜索结果。
- 扫描达到 10,000 条限制时，不删除未扫描区域的旧索引，避免把“未看见”误判为“已删除”。
- 搜索索引仍是应用数据目录中的本地缓存；不修改 `.mdx` 文件格式，不向用户文档写入索引元数据。

## 3. 非目标

- 不增加实时文件监听、事件防抖队列或后台常驻 watcher。
- 不增加索引进度条、取消按钮、独立索引任务中心或数据库。
- 不改变左侧文件树的展示规则、10,000 条安全上限或多文档编辑状态。
- 不把工作区查找改造成跨设备、云端或语义搜索。
- 不删除、重命名、移动或修改工作区中的用户文件。

实时监听的升级触发条件是：用户明确要求 Mora 保持前台时，外部文件变化必须在一秒内自动出现。当前需求通过打开、恢复、窗口聚焦和手动刷新覆盖。

## 4. 方案比较

### 4.1 方案 A：复用扫描结果的刷新驱动增量索引

一次 Rust command 完成目录扫描、磁盘版本比较和必要文件解析，返回目录树与索引统计。前端在既有刷新入口调用该 command。

优点：

- 不增加依赖和后台生命周期。
- 一次目录遍历同时服务文件树和索引，避免重复扫描。
- 增量判断与文件读取都在 Rust 内完成，路径和格式校验边界清晰。
- 窗口聚焦与手动刷新已经存在，前端改动集中。

缺点：文件变化不会在 Mora 始终保持前台时立即出现，需要下一次手动刷新或重新聚焦。

### 4.2 方案 B：Rust 文件监听器持续推送变化事件

使用文件监听库监控每个工作区根目录，将创建、修改、删除和重命名事件防抖后推送到前端或索引服务。

优点：变化接近实时。

缺点：需要处理 watcher 生命周期、根目录增删、重复事件、重命名配对、队列溢出、编辑器自身保存事件和平台差异。当前没有一秒内实时刷新的确认需求，复杂度无法证明必要。

### 4.3 方案 C：每次刷新完整重建索引

每次扫描后重新解析工作区内全部正文并覆盖索引。

优点：实现最直接，不需要持久化磁盘版本。

缺点：每次聚焦都重复打开所有 ZIP 和 Markdown 文件，大工作区成本随文件数线性增长，不满足“增量刷新”。

采用方案 A。方案 B 仅在实时性指标被明确提出时增加；方案 C 不满足已确认需求。

## 5. 数据模型

### 5.1 索引项磁盘版本

在现有 `NoteIndexEntry` 中增加可选字段：

```text
sourceRevision?: {
  modifiedAtMs: u128,
  size: u64
}
```

字段使用 `serde(default)` 保持现有 JSON 数组兼容。旧索引项首次进入工作区刷新时没有版本，视为需要重新读取；刷新成功后写入版本。打开和保存单篇笔记的既有 upsert 也记录当前磁盘版本。

索引项继续保留规范文件路径、标题、标签、摘要、更新时间和正文。磁盘版本只用于判断是否需要重读，不参与搜索排序，也不暴露为用户文档格式。

### 5.2 刷新结果

Rust command 返回：

```text
WorkspaceRefreshResult {
  folder: FolderScan,
  index: WorkspaceIndexRefresh
}

WorkspaceIndexRefresh {
  discovered: usize,
  indexed: usize,
  unchanged: usize,
  removed: usize,
  failed: Vec<WorkspaceIndexFailure>,
  truncated: bool
}
```

`discovered` 是本次扫描可见的 Markdown 文件数；`indexed` 包含新增和成功更新；`unchanged` 是版本相同而跳过正文解析的数量；`removed` 是确认删除后移出的旧索引；`failed` 包含路径和稳定的用户可读错误，不包含文件正文或敏感内容。

## 6. Rust 设计

### 6.1 目录扫描

保留 `workspace::scan_folder` 和当前过滤、自然排序、符号链接跳过及 10,000 条限制。增加一个只遍历 `FolderScan.entries` 的文件路径收集函数，不再次访问磁盘。

Tauri 层以新的 `refresh_workspace_folder` command 取代前端对 `scan_workspace_folder` 的调用：

1. 在阻塞任务中调用 `scan_folder`。
2. 从扫描树收集 `.md`、`.mdx` 路径。
3. 调用批量索引刷新。
4. 返回同一次扫描得到的目录树和索引统计。

使用 Tauri 异步 command 包装阻塞任务，避免大量 ZIP/文本读取占用 UI command 线程。不增加队列、worker 服务或后台状态机。

### 6.2 批量索引

`note_index.rs` 增加一次读、一次写的批量刷新函数：

1. 读取全部现有索引项；损坏索引继续沿用当前“空索引恢复”语义。
2. 用 `path_identity` 生成大小写稳定的路径键，消除 Windows 路径大小写和等价路径重复。
3. 对每个扫描文件读取当前 `DiskRevision`。
4. 已有索引版本相同则计入 `unchanged`。
5. 新增、版本缺失或版本变化时调用加载函数：
   - `.mdx`：复用 `read_mdx`，执行已有 archive 和 manifest 校验。
   - `.md`：复用 `import_markdown_file`，映射标题、标签、摘要和正文。
6. 成功时替换索引项并计入 `indexed`；失败时保留旧项并记录失败。新文件失败时不会产生索引项。
7. 扫描未截断时，删除位于当前根目录下但不在本次文件集合中的旧项；扫描截断时跳过删除阶段。
8. 按更新时间排序，并只写一次 `notes-index.json`。

### 6.3 并发与写入完整性

现有打开、保存、列表、搜索和批量刷新都访问同一个 JSON 文件。`note_index.rs` 使用一个进程内标准互斥锁串行化完整的读改写操作，防止两个并发 command 相互覆盖。

锁只保护索引缓存，不包围目录扫描；批量刷新在取得锁后读取需要变化的文件并一次写入，保证比较基于同一索引快照。单篇 upsert、列表和搜索复用同一锁，不创建接口、仓储层或数据库。

索引仍使用临时文件写入。若替换失败，返回错误且不把成功统计报告给前端；用户源文件不受影响。

## 7. 前端设计

### 7.1 `useDocumentSession`

新增一个私有 `refreshFolder(path)` 辅助函数，负责：

- 调用 `refresh_workspace_folder`。
- 把 `result.folder` 映射成现有 `WorkspaceFolder`。
- 保留目录身份、不可用状态和现有警告规则。
- 返回索引统计供调用者汇总。

`openFolder`、会话恢复和 `refreshFolders` 都复用该函数，删除当前三份重复的扫描映射代码。`refreshFolders` 返回所有成功根目录的索引统计；一个根目录失败不阻止其他根目录刷新。

### 7.2 刷新入口

- 打开文件夹：扫描并完成首次批量索引后再显示成功状态。
- 恢复会话：逐个恢复目录树并建立或增量更新索引；单个失败继续加入 warnings。
- 窗口聚焦：沿用现有 `refreshFolders`，因此同时刷新目录树和索引。
- 左侧刷新按钮：补齐 `WorkspaceSidebar` 的 `refresh-folder` 事件接线，只刷新目标根目录。
- 工作区查找刷新：先刷新所有打开文件夹，再重新调用 `list_notes` 或 `search_notes`，确保显示本次索引结果。

手动操作完成后，状态栏显示汇总，例如“索引已刷新：更新 3，移除 1，跳过 42，失败 1”。后台恢复和聚焦刷新只在失败时显示现有错误提示，避免正常聚焦反复产生通知。

### 7.3 搜索面板

搜索面板继续使用现有 `list_notes` 和 `search_notes`，不增加第二份搜索状态。空状态文字改为说明：打开工作区会自动建立索引，也可以手动刷新。

本次不改变全局本地索引的结果范围。关闭文件夹不会删除其有效缓存；再次打开或刷新该根目录时处理变化和删除。这样保留现有“本地笔记库”语义，同时让当前工作区无需逐篇打开即可搜索。

## 8. 错误处理

- 根目录无法读取：该目录树标记不可用，不修改其索引，也不影响其他根目录。
- 单文件缺失、读取失败或格式无效：记录失败，保留旧索引，继续处理后续文件。
- 磁盘版本读取失败：按单文件失败处理，不把它误判为删除。
- 扫描截断：返回 `truncated: true`，索引可见部分，但不执行删除阶段；前端沿用目录截断提示。
- 索引文件损坏：沿用现有空索引恢复语义，本次可读取文件重新建立索引。
- 索引写入失败：command 失败，前端保留现有目录状态并显示错误；不修改用户笔记。

## 9. 测试设计

### 9.1 Rust 单元与集成测试

- 首次批量索引 `.md` 与合法 `.mdx`，无需先在 Mora 中打开。
- 第二次刷新版本不变时全部计入 `unchanged`，加载器不被调用。
- 修改文件后只更新目标项；新增文件被加入；删除文件被移出。
- 损坏 `.mdx` 和不可读文件不终止批次，并保留上次有效索引。
- 旧 JSON 索引缺少 `sourceRevision` 时可以读取并在下一次刷新升级。
- Windows 等价路径不会产生重复项。
- 截断扫描不会删除未扫描旧项。
- 并发 upsert 与批量刷新不会生成损坏 JSON 或丢失完整写入。

### 9.2 前端测试

- 打开、恢复和聚焦刷新调用新 command，并消费同一返回目录树。
- `refreshFolders` 汇总多个根目录且隔离单目录失败。
- 左侧刷新按钮只刷新目标根目录。
- 工作区查找刷新先增量索引，再读取列表或重新搜索。
- 手动刷新显示更新、删除、跳过和失败统计。
- 搜索空状态文案反映工作区自动索引行为。

## 10. 当前必须、条件升级与本次不实现

### 10.1 当前必须实现

- 同一次工作区扫描产生目录树和待索引文件集合。
- 首次批量索引与基于磁盘版本的增量更新。
- 新增、变化、删除、失败和截断语义。
- 索引并发保护及单次批量写入。
- 打开、恢复、聚焦、侧栏和搜索面板刷新入口。
- Rust 与前端回归测试。

### 10.2 仅在指标不达标时增加

- 实时 watcher：只有前台一秒内更新成为明确验收指标时增加。
- 进度与取消：只有 10,000 条安全上限内的首次索引在目标机器上持续超过 2 秒并影响操作时增加。
- 数据库或倒排索引：只有当前 JSON 搜索在 10,000 篇索引内的实测查询持续超过 200 毫秒时评估。

### 10.3 本次不实现

- 文件监听依赖和后台事件队列。
- SQLite、全文搜索数据库或语义向量索引。
- 工作区范围过滤、排除规则配置和索引管理界面。
- 修改 `.mdx` 格式或把索引写入用户目录。

## 11. 删减检查

| 新增内容 | 解决的需求 | 现有能力不能直接承担的原因 | 删除后失败的验收项 |
| --- | --- | --- | --- |
| `sourceRevision` 可选字段 | 跳过未变化正文 | 当前索引没有磁盘版本 | 增量刷新退化为全量解析 |
| 批量刷新函数 | 一次处理新增、变化和删除 | 现有 upsert 每篇读取并重写整个 JSON，不能判断删除 | 批量索引、删除清理和单次写入失败 |
| `refresh_workspace_folder` command | 一次扫描同时服务目录树和索引 | 前端不能读取或校验本地正文，分开 command 会重复扫描 | 首次批量索引或刷新性能验收失败 |
| 索引互斥锁 | 防止并发读改写覆盖 | 当前单篇操作较少，但批量刷新会与打开、保存和搜索并发 | 索引 JSON 完整性和更新不丢失失败 |
| `useDocumentSession` 私有刷新辅助函数 | 统一打开、恢复和刷新行为 | 当前三处扫描映射重复，新增索引结果会继续分叉 | 不同入口索引行为不一致 |

未增加 watcher、数据库、任务中心、接口、工厂、注册中心或第二份搜索状态。所有新增内容都直接对应已确认验收项。
