# Mora 附件管理设计

**日期：** 2026-08-24  
**状态：** 已批准  
**范围：** 当前文档中的普通附件，不包含图片资产管理

## 背景

Mora 已支持选择或拖入资源：图片进入 `assets/`，普通文件进入
`attachments/`，并把相应 Markdown 引用插入正文。现有保存流程会把新资源写入
`.mdx`，同时保留旧归档中的所有资源。

这条链路能够“导入附件”，但还不能“管理附件”：用户看不到正文未引用的附件，
不能只添加不插入、重命名显示名称、打开、另存或删除附件。只修改
`meta.attachments` 也不足以删除附件，因为当前 ZIP 重建逻辑会继续复制原二进制条目。

## 已确认需求

### 当前必须实现

1. 当前文档提供独立的附件管理面板。
2. 面板展示 `meta.attachments` 中的全部附件，包括正文未引用的附件。
3. 支持一次选择多个普通文件并添加到当前文档，但不自动插入正文。
4. 每个附件支持：
   - 插入 Markdown 引用；
   - 使用系统默认应用打开；
   - 另存到用户选择的位置；
   - 修改用户可见的文件名；
   - 删除。
5. 删除、重命名和添加只修改当前未保存会话；保存成功后才真正改写 `.mdx`。
6. 正文仍引用附件时阻止删除，提示用户先移除正文引用。
7. 草稿恢复要保留新增附件、元数据变化和待删除路径。
8. 另存为新 `.mdx` 时必须从原文档复制全部保留资源，不能丢失未加载或正文未引用的附件。
9. 所有包内路径继续使用 `attachments/<stored-name>`，禁止 Blob URL 进入正文、草稿或保存请求。

### 仅在指标不达标时增加

- 当单篇文档附件超过 200 个且面板首次渲染超过 100ms 时，再增加虚拟列表。
- 当用户实际需要跨附件批处理时，再增加多选删除或批量另存。
- 当缓存目录可测量增长失控时，再增加按时间清理；首版使用每个附件一个固定预览目录，打开前清理该目录，天然限制为一个当前副本。

### 本次不实现

- 图片资产管理。
- 附件目录、排序、标签或文件夹层级。
- 在外部程序中编辑附件后自动回写。
- 附件内容全文索引。
- 加密、云同步或共享链接。
- 通用资源插件协议、资源仓库接口或第二套附件数据库。

## 方案比较

### 方案 A：会话内延迟变更，随文档保存提交（采用）

附件操作进入当前文档的资源会话和元数据，遵循现有 dirty、草稿、冲突检测、
历史快照和安全保存流程。保存请求显式携带待删除路径，Rust 重建 ZIP 时过滤这些条目。

优点：附件变更和正文变更拥有完全相同的撤销关闭语义；保存失败不损坏磁盘；不需要
第二套事务。代价是资源会话需要记录待删除路径。

### 方案 B：每次操作立即改写 `.mdx`（不采用）

每次删除或重命名都直接运行后端命令重建归档。虽然单次命令直观，但会绕过 dirty、
关闭确认、外部冲突和草稿恢复；正文未保存时附件已经落盘，用户无法整体放弃修改。

### 方案 C：附件独立存储或数据库（不采用）

把附件放在外部目录或应用数据库，再由 `.mdx` 引用。该方案直接破坏 Mora 单文件封装目标，
并引入同步、一致性和迁移问题。

## 交互设计

### 入口与布局

在“插入·Markdown”菜单中保留“导入图片或附件”，并新增“附件管理”。后者打开
`AttachmentPanel` 模态面板。面板打开后接管焦点，背景点击或关闭按钮退出，不切换文档。

标题区显示当前文档名、附件数量和“添加附件”按钮。每个附件行显示：

- 原始文件名 `originalName`；
- MIME 类型；
- 格式化后的大小；
- “正文已引用”或“未引用”状态；
- 打开、插入引用、另存为、重命名、删除操作。

没有附件时展示明确空状态。添加附件使用现有多选文件对话框；如果所选文件被识别为图片，
不把它伪装成普通附件，而是跳过并提示用户使用现有图片导入入口。

### 重命名

重命名使用行内输入框，保存和取消均可键盘操作。新名称去除首尾空白并拒绝空字符串；
显示名称允许重复，因为包内路径仍唯一。重命名只修改 `originalName`，不修改
`storedName`、`path` 或正文链接。

### 插入引用

插入格式固定为：

```markdown
[显示文件名](attachments/stored-name.ext)
```

编辑器显示层可将该包内路径投影为对象 URL，但当前规范 Markdown 始终保留相对路径。

### 删除

点击删除后在当前行显示二次确认。删除前使用统一的资源引用提取函数检查规范正文：

- 如果正文仍引用该 `attachments/...` 路径，阻止删除并提示先删除正文引用；
- 如果未引用，则从当前元数据移除，并让资源会话记录删除；
- 如果附件是本次尚未保存的新资源，只撤销对象 URL 和待写入数据，不把路径加入后端删除列表；
- 如果资源会话中的附件是新资源，只从待写入队列移除；已加载的旧附件或未加载但存在于
  metadata 的附件加入 `removedResources`，保存时再过滤 ZIP 条目。

删除不会自动改写正文，也不会留下已知失效链接。

## 前端数据模型

### 资源引用提取

扩展 `src/utils/resourcePaths.ts`，增加：

```ts
export function referencedResourcePaths(markdown: string): Set<string>;
```

它与现有 Markdown 目标、HTML `src`/`href` 替换共用同一匹配规则，成为打开资源按需加载和
附件删除检查的唯一入口，避免维护第二份正则。

### ResourceSession

在现有 `createResourceSession()` 中增加：

```ts
resource(path: string): ResourceSaveData | null;
rename(path: string, originalName: string): void;
remove(path: string): void;
removedResources(): string[];
```

快照扩展为：

```ts
type ResourceSessionSnapshot = {
    newResources: ResourceSaveData[];
    removedResources: string[];
};
```

`register`、`rename`、`remove` 和 `clear` 继续维护 revision；`markSaved()` 把新资源标记为已保存，
并清空已提交的删除集合。返回值全部复制，外部不能修改内部 Map。

### 文档会话

草稿 `DraftSnapshot` 增加 `removedResources`。旧草稿缺少该字段时按空数组恢复。

保存和另存为的稳定快照包含：规范正文、元数据、新资源和待删除路径。保存期间如果任一部分
变化，文档保持 dirty，且只清理已实际提交的资源变更。

附件增删改通过文档会话更新元数据并调度草稿，不能只改 Vue 组件局部状态。

## 保存协议与 ZIP 语义

前后端保存请求增加：

```ts
removedResources: string[];
```

Rust 对每个路径复用资源路径校验，只接受 `assets/<file>` 或 `attachments/<file>` 的单层安全路径；
本功能界面只会提交 `attachments/`。

`build_mdx_archive` 改为明确区分：

- `source_path`：资源和历史从哪里读取；
- `target_path`：安全写入到哪里。

普通保存时二者相同。另存为时 `source_path` 是当前已保存 `.mdx`，`target_path` 是新位置；
无源文档则只写入 `newResources`。这同时修复现有另存为可能从错误目标归档保留资源、或在新目标
丢失旧资源的问题。

已有源文档若缺失或损坏，保存必须明确失败，不能生成 metadata 仍指向附件但 ZIP 已丢失二进制
的破损副本。仅当同名 `.bak` 是现有安全保存流程留下的可校验备份时，允许从该备份保留资源并
继续恢复。

归档重建顺序：

1. 从源归档收集安全、允许保留的资源和历史条目；
2. 过滤 `removedResources`；
3. 追加旧文档历史快照并轮转到 20 条；
4. 写 manifest、meta、content；
5. 写保留条目；
6. 写新资源，同名新资源覆盖保留条目；
7. 验证新 ZIP 并通过现有 `.tmp + .bak` 流程替换目标。

元数据上，已有同路径条目更新 MIME、大小和显示名称时保留 `id`、`createdAt`；新路径才生成新 ID。

## 打开与另存附件

Rust 增加附件读取请求，数据来源二选一：

- 已保存附件：源 `.mdx` 路径和安全包内路径；
- 未保存新附件：前端资源会话中的 Base64。

两条路径最终复用同一个字节读取与大小校验函数。

“打开”把字节写到应用缓存目录的固定附件预览子目录。目录键由文档 ID 和包内存储名组成；
每次打开前只清理该附件自己的预览目录，再用经过文件名字符清理的 `originalName` 写入。
然后通过 Rust 侧 `tauri-plugin-opener` 调用系统默认应用。前端不获得任意缓存路径，也不需要
opener capability。

“另存为”先让用户选择目标，再由 Rust 使用现有安全写文件能力落盘。取消选择不调用后端，
写入失败不留下半成品。

外部程序修改预览副本不会回写 `.mdx`，面板明确把“打开”视为只读副本操作。

## 错误与并发

- 打开、另存或导入期间切换活动文档时，延迟结果不得污染新文档。
- 源归档缺失、附件条目缺失、Base64 无效或路径不安全时返回中文错误，并保持附件元数据和 dirty 状态。
- 重复保存继续使用已有 saving guard。
- 外部文件冲突继续走现有重新加载、覆盖、另存为流程；附件变更不绕过冲突判断。
- 删除列表中重复路径先去重；删除不存在条目幂等，不影响其他资源。

- `resourcePaths`：Markdown 链接、图片、HTML 属性、外部 URL 和去重。
- `ResourceSession`：重命名、新资源删除、已保存资源删除、快照恢复、保存后清理和 URL 回收。
- `useDocumentSession`：保存请求、另存为源路径、草稿恢复、保存期间资源继续变化。
- `AttachmentPanel`：空状态、列表、引用状态、行内重命名、删除确认、引用阻止提示和事件负载。
- `App`：菜单入口、添加不插入正文、插入规范引用、跨文档异步隔离、打开与另存请求。

### Rust 自动测试

- 删除一个附件时 ZIP 和 metadata 同时移除，其他资源保持不变。
- 重复和非法删除路径被正确处理。
- 另存为复制源归档资源，不读取目标归档的旧资源。
- 已保存附件和 Base64 附件读取结果一致。
- 缓存文件名不允许目录穿越，固定预览目录只保留当前副本。
- 附件另存失败不破坏已有目标。

## 最小化审查

| 新增项 | 解决的已确认需求 | 现有组件不能直接承担的原因 | 删除后的失败验收项 |
| --- | --- | --- | --- |
| `AttachmentPanel.vue` | 附件列表和行级管理交互 | 现有历史、工作区面板的数据和操作语义不同 | 用户无法查看和管理附件 |
| `removedResources` 会话状态 | 延迟、可放弃的物理删除 | 单靠 metadata 无法阻止 ZIP 复制旧二进制 | 保存后被删附件仍存在包内 |
| Rust 附件读取/导出命令 | 打开和另存包内或待保存附件 | 前端不能直接读取 ZIP 或安全写任意本地路径 | 打开、另存操作不可用 |
| `tauri-plugin-opener` Rust 依赖 | 交给系统默认程序打开 | 标准库没有跨平台默认应用 API，自写平台命令风险更高 | “打开附件”验收失败 |

除以上项目外不增加模块、接口、数据库或第三方依赖。每项都直接对应当前验收需求。
